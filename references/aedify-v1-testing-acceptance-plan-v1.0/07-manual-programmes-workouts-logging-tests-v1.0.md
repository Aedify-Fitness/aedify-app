## Non-Negotiable Acceptance Principles

- No test may approve behavior that expands product scope beyond the re-locked PRD.
- Local-only/offline-first behavior must be proven for every non-AI feature.
- BYOK secrets must never appear in Drift, `shared_preferences`, local files, logs, Crashlytics, exports, screenshots generated by tests, or debug fixtures.
- Durable structured app data belongs in Drift/SQLite. Simple non-critical preferences may use `shared_preferences`. Secrets use `flutter_secure_storage` only.
- AI outputs are never trusted directly. They must pass schema validation, deterministic business-rule validation, exercise matching, privacy filtering, and user review where required.
- Crashlytics is allowed only for crash diagnostics with strict redaction.
- Imported workouts/programmes, AI-generated workouts/programmes, and shared plans must never bypass preview/review/validation gates.
- Progress media and physique-analysis data stay local by default and are excluded from normal export/share flows.

## Manual Workout Builder Tests

### Creation Cases

| ID | Scenario | Expected Result |
|---|---|---|
| MAN-WO-001 | Create empty workout name only | Block save until required exercise/set data exists or save draft if allowed. |
| MAN-WO-002 | Add strength exercise with working sets | Set prescriptions save correctly. |
| MAN-WO-003 | Add warm-up sets | Warm-up sets marked `warmup`; visible in plan/log. |
| MAN-WO-004 | Add cardio/time-based exercise | No invalid strength-only fields required. |
| MAN-WO-005 | Add mobility/recovery exercise | Correct modality handling. |
| MAN-WO-006 | Reorder exercises | Order persists. |
| MAN-WO-007 | Delete exercise | Child set prescriptions delete safely. |
| MAN-WO-008 | Duplicate exercise in same workout | Allowed or clearly blocked by product decision; no key conflicts. |

### Validation Cases

- Reps must be positive where required.
- Sets must be positive.
- Weight may be optional for bodyweight/cardio/mobility as appropriate.
- RPE/RIR ranges must be valid.
- Rest duration must be non-negative.
- Warm-up percentage values must be valid if user manually enters them.
- Superset members must have valid execution group IDs.

## Active Workout Logger Tests

### Happy Path

Steps:

1. Start workout from manual programme.
2. Log each set.
3. Add RPE/RIR and notes.
4. Mark set completed.
5. Complete workout.
6. View workout history.

Expected:

- Active workout state persists during app backgrounding.
- Completed workout is saved transactionally.
- Programme next-session state updates if applicable.
- Analytics can read completed working sets.

### Interruption Cases

| Case | Expected Result |
|---|---|
| App backgrounded mid-set | Active state preserved. |
| App killed mid-workout | Recover active workout or clearly restore last saved state. |
| Device restarts | No corrupted partial completion. |
| Completion transaction fails | Active workout remains recoverable; no duplicate completed workout. |
| User cancels workout | Confirm destructive action; no completed log created. |
| User edits previous set | Changes persist and analytics update. |

## Set Type Tests

Warm-up and working set behavior:

- Warm-up sets visible in workout history.
- Warm-up sets excluded from PR detection.
- Warm-up sets excluded from e1RM.
- Warm-up sets excluded from plateau detection.
- Working sets drive analytics.
- Changing a set from warm-up to working updates analytics after recalculation.
