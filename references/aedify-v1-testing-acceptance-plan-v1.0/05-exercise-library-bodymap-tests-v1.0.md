## Non-Negotiable Acceptance Principles

- No test may approve behavior that expands product scope beyond the re-locked PRD.
- Local-only/offline-first behavior must be proven for every non-AI feature.
- BYOK secrets must never appear in Drift, `shared_preferences`, local files, logs, Crashlytics, exports, screenshots generated by tests, or debug fixtures.
- Durable structured app data belongs in Drift/SQLite. Simple non-critical preferences may use `shared_preferences`. Secrets use `flutter_secure_storage` only.
- AI outputs are never trusted directly. They must pass schema validation, deterministic business-rule validation, exercise matching, privacy filtering, and user review where required.
- Crashlytics is allowed only for crash diagnostics with strict redaction.
- Imported workouts/programmes, AI-generated workouts/programmes, and shared plans must never bypass preview/review/validation gates.
- Progress media and physique-analysis data stay local by default and are excluded from normal export/share flows.

## Dataset Persistence Tests

Assertions:

- Exercise `id` is stable and stored as int for Firebase records.
- `source = firebase` for synced records.
- `primary_muscles` preserves granular source values.
- `muscle_groups` stores 14-bucket values.
- `category` is preserved after typo normalization.
- `equipment = category` only when modality is strength.
- Non-strength records have null equipment where specified.
- Videos are stored in child table with cascade delete.
- Favorites/substitutions survive dataset refresh where source exercise remains.

## Search + Filter Tests

Required filters:

- Text search by exercise name.
- Muscle group filter.
- Equipment filter.
- Difficulty filter.
- Modality filter.
- Favorites only.
- Substitution/avoid list behavior.

Edge cases:

- Empty search.
- No results.
- Case-insensitive search.
- Search with special characters.
- Combined filters that produce zero results.
- Very large result list scroll performance.

Acceptance:

- Search uses local data only after sync.
- Filters are deterministic and do not require network.
- Filter state does not corrupt favorites/substitution state.

## Exercise Detail Tests

Test cases:

1. Detail screen shows name, difficulty, muscles, equipment/modality, force/mechanic where available.
2. Steps render in correct order.
3. Missing mechanic/force renders cleanly.
4. Videos render male/female and front/side metadata where available.
5. Video playback error shows retry/fallback and does not block text instructions.
6. Favorite toggle persists.
7. Substitute/avoid toggle persists and affects candidate generation later.
8. Custom exercise detail works without videos.

## TTS/Audio Tests

Test cases:

- Generate audio for exercise steps if feature path is implemented.
- Cache per exercise/step/locale.
- Cache hit avoids regeneration.
- Cache file missing triggers regeneration or graceful fallback.
- TTS unavailable shows readable text fallback.
- Audio cache metadata is deleted when custom exercise is deleted.

Acceptance:

- TTS is optional enhancement; exercise instructions remain usable without it.
- Audio cache does not store private data.

## Bodymap Tests

### Asset Contract

Required checks:

- Front and back SVGs load successfully.
- Each interactive path maps to one of the 14 UI muscle buckets.
- No path maps to an unknown muscle group.
- All 14 expected buckets are represented where anatomically applicable.
- Tap areas are large enough for practical mobile interaction.
- Highlight state updates correctly.
- Bodymap filter matches library muscle group filter.

### Bodymap Interaction Cases

| Case | Expected Result |
|---|---|
| Tap Chest front | Library filters to Chest exercises. |
| Tap Back rear | Library filters to Back exercises. |
| Tap Quads front | Library filters to Quads exercises. |
| Tap Hamstrings rear | Library filters to Hamstrings exercises. |
| Tap overlapping shoulder/traps area | Correct path priority or disambiguation. |
| Clear selection | Library returns to previous unfiltered state. |
| Dark/light theme | SVG remains visible. |
| Font scaling | Bodymap layout remains usable. |

## Candidate Engine Dependency Tests

Although AI generation is tested later, M2 must provide correct library data for candidate lists.

Tests:

- Hard filter by equipment.
- Hard filter by experience/difficulty.
- Soft rank by goals.
- Include adjacent compatible movements where allowed.
- Exclude substituted/avoided exercises.
- Preserve custom exercise eligibility where required later.

Acceptance:

- Candidate engine has deterministic fixture output.
- AI cannot receive exercise IDs that are unavailable to the user constraints.

## Performance Tests

Minimum checks:

- Initial dataset parse/persist completes within acceptable private-release tolerance.
- Library search feels responsive with full dataset.
- Bodymap filter response is immediate after local sync.
- Exercise detail opens without long blocking operations.
- Video thumbnails/metadata do not freeze list scrolling.
