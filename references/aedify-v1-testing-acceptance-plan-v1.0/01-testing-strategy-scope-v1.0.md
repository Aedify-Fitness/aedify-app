## Goal

Define the testing strategy that governs the v1 implementation. The app is local-only, offline-first, BYOK-based, and private-release scoped, so the testing strategy must emphasize local data correctness, privacy boundaries, deterministic validation, AI failure containment, and cross-platform parity rather than backend-scale testing.

## Non-Negotiable Acceptance Principles

- No test may approve behavior that expands product scope beyond the re-locked PRD.
- Local-only/offline-first behavior must be proven for every non-AI feature.
- BYOK secrets must never appear in Drift, `shared_preferences`, local files, logs, Crashlytics, exports, screenshots generated by tests, or debug fixtures.
- Durable structured app data belongs in Drift/SQLite. Simple non-critical preferences may use `shared_preferences`. Secrets use `flutter_secure_storage` only.
- AI outputs are never trusted directly. They must pass schema validation, deterministic business-rule validation, exercise matching, privacy filtering, and user review where required.
- Crashlytics is allowed only for crash diagnostics with strict redaction.
- Imported workouts/programmes, AI-generated workouts/programmes, and shared plans must never bypass preview/review/validation gates.
- Progress media and physique-analysis data stay local by default and are excluded from normal export/share flows.


## Test Pyramid for v1

| Layer | Purpose | Required Coverage |
|---|---|---|
| Static analysis | Catch type, lint, dead-code, and unsafe dependency issues early | Every PR |
| Unit tests | Validate pure business logic, validators, mappers, schema guards, calculations | Core domain, data, AI validation, import/export DTOs |
| Repository tests | Validate Drift DAOs, transactions, migrations, query correctness | Every durable data area |
| Provider/controller tests | Validate Riverpod state machines without UI coupling | Onboarding, sync, logging, AI flows, imports, media flows |
| Widget tests | Validate key screen states and form behavior | Core screens, review gates, error states |
| Integration tests | Validate end-to-end flows on emulator/simulator/real devices | Critical journeys |
| Manual exploratory QA | Catch UX, media, device permission, and real-provider issues | Before milestone sign-off and private release |
| Privacy/security tests | Prove forbidden data does not leak | Every export/log/Crashlytics/AI payload path |

## Quality Gates

### Gate A — Code-Level Readiness

A feature may enter QA only when:

- Static analysis passes.
- Unit tests for all new pure logic pass.
- Repository tests pass for any schema/query/migration change.
- All relevant fake services are updated.
- Feature flags or navigation guards prevent half-built flows from being reachable in release builds.
- No TODO allows unsafe persistence, raw AI saves, skipped validation, or logging sensitive data.

### Gate B — Feature Acceptance

A feature is accepted only when:

- Happy path works on iOS and Android.
- Empty state works.
- Offline state is defined and tested.
- Error state is user-readable and recoverable.
- Data survives app restart if it is durable.
- Abandoned drafts/artifacts follow lifecycle rules.
- The feature cannot corrupt active programmes/logs.
- Required user-review gates cannot be skipped.
- The feature does not introduce product scope beyond the PRD.

### Gate C — Privacy Acceptance

A feature is accepted only when:

- Secrets never appear outside `flutter_secure_storage`.
- Drift does not store API keys or raw provider secrets.
- `shared_preferences` stores only non-critical settings.
- Crashlytics context contains only allowed non-sensitive metadata.
- Debug logs do not print prompts, AI responses, keys, candidate lists, logs, measurements, injuries, media paths, source excerpts, or imports.
- Exports contain only explicitly allowed fields.
- Temporary files have cleanup tests.

### Gate D — AI Acceptance

An AI feature is accepted only when:

- It blocks before prompt assembly if prerequisites fail.
- It uses the correct operation subtype.
- It sends the minimum required context.
- It validates structured JSON locally.
- It performs one automatic repair attempt only where allowed.
- It fails safely into `needs_input`, `blocked`, or user-readable error states.
- It never persists app-actionable output without validation and required user confirmation.
- It respects candidate exercise IDs and never invents local database IDs.

### Gate E — Release Acceptance

The release candidate is accepted only when:

- All milestone gates pass.
- All blocking defects are closed.
- App installs cleanly on fresh iOS and Android devices.
- App upgrades cleanly from seeded older local schemas.
- Crash reporting works without sensitive payloads.
- Private release distribution is configured for maximum 5 users.
- The final smoke test covers onboarding → sync → build/log workout → analytics → export → AI call failure/success path.

## Blocking Defect Categories

Any defect in these categories blocks release:

1. Secret leakage.
2. Crashlytics sensitive payload leakage.
3. Local DB corruption or irreversible data loss.
4. AI/import draft persisted without review/validation.
5. Wrong exercise IDs saved due to matching bug.
6. Progress media exported or logged against rules.
7. Image import artifacts retained after save/cancel beyond lifecycle rules.
8. BYOK provider call made without explicit consent for imports/media.
9. Non-AI feature unusable offline after initial exercise sync.
10. App cannot complete onboarding on either target platform.
11. App cannot log a workout reliably.
12. `.aedifyplan` import/export schema accepts malformed or unsafe data.
13. Broken migrations from any released private-test build.
14. Reproducible crash loop on launch.

## Non-Blocking Defect Examples

These may be deferred if documented:

- Minor copy issue that does not affect consent or safety.
- Minor visual misalignment outside core logging/import flows.
- Slow animation not affecting data correctness.
- Missing non-critical empty-state illustration.
- Optional exercise-instructions appendix formatting issue if PDF core prescription is correct.

## Test Data Classification

| Test data type | Allowed location | Notes |
|---|---|---|
| Synthetic exercise fixtures | Repo test fixtures | May mirror Firebase shape, not user data. |
| Synthetic profile fixtures | Repo test fixtures | Must not contain real user identity. |
| Synthetic logs | Repo test fixtures | Use clearly fake dates/names. |
| Synthetic AI responses | Repo test fixtures | Must avoid source excerpts from paid materials. |
| Synthetic screenshots | Repo test fixtures | Use artificial programme tables only. |
| Real API keys | Local developer machine secure storage only | Never committed, printed, or attached. |
| Real progress photos | Not allowed in repo | Use generated silhouettes/placeholders for tests. |

## Test Automation Requirements

- All deterministic business rules must be unit-testable without Flutter UI.
- Drift schema and migration tests must run in CI with an in-memory or test database.
- Riverpod controllers must be testable with fake repositories and fake AI providers.
- Import/export DTOs must have golden fixture tests.
- AI structured-output validators must have valid, invalid, repairable, and non-repairable fixtures.
- Privacy filters must have tests that deliberately inject forbidden fields and verify removal/rejection.

## Manual QA Requirements

Manual QA is required for:

- Platform permissions: camera, gallery, health, notifications, files/share sheet.
- Real video playback behavior.
- Local PDF output readability.
- Native share sheet behavior.
- Real BYOK provider smoke tests.
- Multimodal provider smoke tests.
- Crashlytics redaction verification in Firebase console.
- Accessibility with VoiceOver/TalkBack.
- Media storage/deletion behavior on real devices.

## Out of Testing Scope for v1

The plan does not require:

- Public-scale load testing.
- Multi-account testing.
- Server backend testing beyond Firebase Storage/Auth/Crashlytics configuration checks.
- Subscription/payment testing.
- Cloud sync conflict testing.
- OCR testing for scanned/image-only PDFs.
- Computer-vision form-check testing.
- Medical safety certification.

## Change Control

If testing reveals a needed behavior change:

1. Classify it as defect, clarification, or product change.
2. If defect: fix within v1 if it violates current PRD.
3. If clarification: update implementation docs without changing scope.
4. If product change: create formal change request/version bump before implementation.
