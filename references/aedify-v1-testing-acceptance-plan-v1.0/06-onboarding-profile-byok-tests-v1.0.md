## Non-Negotiable Acceptance Principles

- No test may approve behavior that expands product scope beyond the re-locked PRD.
- Local-only/offline-first behavior must be proven for every non-AI feature.
- BYOK secrets must never appear in Drift, `shared_preferences`, local files, logs, Crashlytics, exports, screenshots generated by tests, or debug fixtures.
- Durable structured app data belongs in Drift/SQLite. Simple non-critical preferences may use `shared_preferences`. Secrets use `flutter_secure_storage` only.
- AI outputs are never trusted directly. They must pass schema validation, deterministic business-rule validation, exercise matching, privacy filtering, and user review where required.
- Crashlytics is allowed only for crash diagnostics with strict redaction.
- Imported workouts/programmes, AI-generated workouts/programmes, and shared plans must never bypass preview/review/validation gates.
- Progress media and physique-analysis data stay local by default and are excluded from normal export/share flows.

## Profile Validation Tests

Required fields:

- Name or display label if required by UX.
- Training experience.
- Goals.
- Schedule/training days.
- Equipment.
- Preferred units.
- Session length.

Validation rules:

- Session duration within allowed increments.
- Training days within supported count.
- Bodyweight non-negative and plausible.
- Height plausible if captured.
- 1RMs plausible if captured.
- Injury/limitations free text never logged to Crashlytics.

## Profile Edit Tests

1. Edit equipment while active programme exists.
2. Edit goal while active programme exists.
3. Edit training days while active programme exists.
4. Edit injury/limitation while active programme exists.
5. Edit substitutions while active programme exists.
6. Edit unit preference after logs exist.

Expected:

- Data saves safely.
- App prompts regeneration/review where active programme may be invalidated.
- Existing historical logs remain canonical and display correctly.
- No automatic destructive changes occur without confirmation.

## Settings Tests

Settings allowed in `shared_preferences`:

- Theme/appearance where applicable.
- Last opened tab/screen if non-critical.
- Non-critical feature hints dismissed.
- Reminder UI preferences if not critical source of schedule truth.

Settings not allowed in `shared_preferences`:

- API keys.
- Programmes.
- Logs.
- Import drafts.
- AI outputs.
- Progress media records.
- Critical schema versions.

Test method:

- Inspect wrapper usage.
- Add unit tests around allowed keys if key registry is implemented.
- Run static grep/audit before release.

## BYOK Secure Storage Tests

### Key Lifecycle

| Case | Expected Result |
|---|---|
| Add OpenAI key | Stored in secure storage only; provider record stores metadata only. |
| Add Anthropic key | Stored in secure storage only. |
| Add Google key | Stored in secure storage only. |
| Read key for provider call | Key retrieved only at call time. |
| Rotate key | Old key removed/replaced. |
| Delete key | AI features disabled or require setup. |
| Secure storage unavailable | User sees recoverable error. |
| App reinstall | Key behavior follows platform secure storage semantics; app handles missing key. |

### Leakage Tests

Inject fake key and verify absent from:

- Drift DB dump.
- `shared_preferences` dump.
- Local files.
- Debug logs.
- Crashlytics custom keys/logs.
- Export files.
- AI request snapshots saved for tests.

## Provider Capability Tests

Capabilities to test:

- Text generation support.
- Native JSON/schema output support.
- Image input support.
- Provider/model availability.
- Max input size metadata if captured.
- Authentication validity.

Scenarios:

1. Valid text-only model.
2. Valid text + JSON/schema model.
3. Valid image-capable model.
4. Invalid key.
5. Rate-limited capability check.
6. Offline capability check.
7. Unknown model.
8. Provider API error.

Expected:

- Capability state updates without exposing key.
- Image import and physique analysis are blocked if no image capability.
- Text-only AI features may remain enabled if text capability exists.
- User gets clear provider setup guidance.

## AI Feature Gate Tests

| Feature | Required Gate |
|---|---|
| AI chat | Valid text-capable provider + key + network. |
| AI workout/programme | Valid text-capable provider + key + required profile/candidate context. |
| Structured save flows | Structured-output validation support locally, with native JSON mode preferred if available. |
| External text import AI parse | Consent + valid text provider + extracted content. |
| Image import | Consent + image-capable provider/model. |
| Physique analysis | Explicit consent + image-capable provider/model + selected media/frames. |

Test cases:

- Missing key blocks all AI calls.
- Unsupported image model blocks image paths before prompt assembly.
- Offline blocks provider calls but leaves local app usable.
- Consent refusal blocks import/media AI call and does not send payload.
